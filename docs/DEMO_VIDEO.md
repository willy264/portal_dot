Cronpot and MeterMend deployment, the complete rental demonstration, community delivery and video publication remain pending. ## Prepare the real footage

1. Complete application deployment and role funding using the [operations guide](../scripts/README.md). Confirm both actual addresses and finalized deployment receipts appear in [the manifest](../deployments/portaldot-v3.json). The deployer, renter and arbiter must be distinct.
2. Seed the camera, printer and drill. Use the camera's 120-second demo dispute window; retain the UI's 24-hour default for ordinary registrations. Start the relayer, confirm its configured signer and keeper mode, and run the complete rehearsal. Preserve `deployments/demo-run.json` and both successful and failed transaction attempts.
3. Confirm the first refund has matching `DepositRefunded` and successful `JobExecuted` events in the same transaction from the configured relayer. The elapsed window alone is not evidence of execution. The current keeper adds a 30-second grace period, so allow at least 150 seconds plus block finality between the return timestamp and the observed refund.
4. Verify the second rental's 30% deduction, approved repair, and income-withdrawal assertion with the reserve unchanged. Check the actual values from this run rather than overlaying planned values on different transactions.
5. Configure DeBox or the preauthorized Telegram fallback and capture an actual delivered notification before including delivery in the narration. A running bot, queued outbox entry or test response does not show delivered community updates. Missing credentials remain a visible pending item.
6. Open the public app on a phone and test its actual QR target. Use the verified public app URL in the closing card; identify the permanent proof page separately. If hosting is still pending, label any localhost recording as a local preview rather than a public deployment.
7. Record at 1920×1080 with a separate voice-over. Frame the mobile browser or narrow the app viewport inside the capture. Set up test wallets before capture; record the approval screen and public account identity without displaying recovery phrases, `.env`, private keys or service credentials. Retain the original, uncut captures outside the public repository.

Use real operator-supplied photos when available. The automated rehearsal also supports [labeled PNG fixtures](../scripts/fixtures/provenance.json); these visibly state that they are not evidence of an actual physical rental or repair. Keep that label in frame and add **“Testnet workflow demonstration · labeled demo images”** when those assets are used. A verified image hash proves byte integrity, not the truth of a damage claim or physical repair. Capture the final stored image, its SHA256, and its actual native store block/index where available.

## Evidence overlays and editing

Use a small consistent overlay: **Portaldot V3 testnet · UTC date/time · block · transaction hash**. Read the actual block and hash from the captured receipt; a dry-run estimate is labeled **simulation**. Show a clear **“120-second dispute window + keeper grace; wait shortened”** card when removing the countdown. Keep the uncut interval in the raw recording. Do not imply that the keeper refunded immediately or that native Scheduler executed the job.

For a fresh seeded camera with zero initial reserve, the script's planned arithmetic is below. These are expected values for rehearsal, not claims of completed transactions:

| Planned stage                                    |      Expected amount |
| ------------------------------------------------ | -------------------: |
| Rental fee / refundable deposit                  |     0.01 / 0.05 tPOT |
| Reserve contribution per rental                  |           0.002 tPOT |
| Reserve after two fees                           |           0.004 tPOT |
| Approved 30% deduction / renter remainder        |   0.015 / 0.035 tPOT |
| Reserve after the deduction                      |           0.019 tPOT |
| Approved half-reserve repair / remaining reserve | 0.0095 / 0.0095 tPOT |
| Operator income from the two fees                |           0.016 tPOT |

Fees, storage deposits and Cronpot tips are separate. Use values recorded by the completed run if the item already had a reserve or another transaction changed its state. Show the actual successful income withdrawal and unchanged reserve; do not invent a failed “withdraw reserve” transaction, because there is no such application function.
