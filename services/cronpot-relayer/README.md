# Cronpot relayer

Run from the repository root with `pnpm --filter @metermend/cronpot-relayer start`. It loads the ignored root `.env` and the deployment manifest. `RELAYER_SEED` controls only the funded testnet worker; the scanner can run without a signing account.

Writes require a verified `executionProfile` in the manifest. The original deployment has no such profile and stays available for indexing only in this version. `READ_ONLY=1` always disables signing. Missing calibration evidence, a changed runtime code hash, or a mismatch in the deployed Cronpot gas getters keeps the signer disabled with an actionable `/health.signerError`. Startup checks existing account mapping without submitting a mapping transaction.

For each refund, the keeper reads the job, rental, account balance, gas price and contract configuration at one finalized snapshot. It runs an initial native simulation and a second native simulation with exactly the finite weight and storage caps of the prepared transaction. Cronpot's `execute` must return ABI `true` from that bounded native pass; an empty return or a caught callback failure blocks broadcast even if the outer call succeeded. An independent Ethereum-context trace at the same hash must contain a successful refund callback, its exact `DepositRefunded` event and `JobExecuted(success=true)` for the correct job and executor. It uses real balances and no state or timestamp overrides. The trace's gas envelope is derived from the configured native storage and fee caps divided by the observed gas price; this spending comparison does not establish an equivalence between native weight and Ethereum gas.

The verified preflight is stored before the exact prepared native transaction is submitted. The runtime identity is checked again before signing; a failed trace, fee check or evidence write prevents broadcast. Simulations do not count as a live refund: only the finalized transaction events establish that result. Calibration files and their SHA-256 hashes are explicit profile inputs, with a reviewed runtime allowlist in `src/execution-profile.ts`; there are no silent execution-budget defaults. The calibration's compiler, raw creation code, constructor arguments and resulting runtime must match the profile. Native `Revive.AccountInfoOf` and `PristineCode` reads must match that runtime bytecode at startup and before each execution.

Profile `verified:true` means the configuration and compiled code were reviewed; it does not mean a refund ran live. `verification.nativeBoundedSuccess` records prior native calibration status and may honestly remain `false` before the first due-job preflight. Every execution still requires a fresh bounded native `true` result and the independent matching event trace. `code.runtimeBytecodeSha256` hashes the constructor-patched runtime, not the compiler's immutable-placeholder template.

The worker indexes finalized native events, including scheduler initialization events with no extrinsic hash. SQLite stores each complete block and cursor atomically. A pruned block reports a history gap and stops cursor advancement. Only jobs owned by MeterMend, targeting MeterMend's `finalizeRefund`, receive this relayer's subsidy; the on-chain Cronpot registry remains generic.

`MODE=native` needs a verified capability in the manifest: P5 transaction/block proof, matching runtime code hash and a separately measured successful execution weight. Otherwise keeper mode executes due jobs after a30-second grace period. Timing uses finalized chain time. Never use a pre-deadline `TooEarly` simulation as the execution budget.

Submission hashes are saved with the job ID and operation. Restarted `executing`, `scheduling`, `execution-unknown` and `native-unknown` jobs pause until reconciliation; they are never blindly broadcast again. Confirmed terminal contract state may settle them. Submitted failures retain their receipt and stop in `manual-review`, including failures discovered during reconciliation. Before any new signed attempt, inspect the original hash, finalized outcome and account nonce / next index; a pending pool transaction must be awaited or deliberately replaced with the same nonce. Failures before a transaction is created can back off, with five attempts maximum. A user may always call MeterMend's time-gated finalization directly.

Endpoints: `/health`, `/jobs`, `/events`. `/events?fromBlock=N` returns complete pages of at most50 blocks, with `throughBlock` and `throughHash`; no query returns the stored workshop history. Finalized block hashes, including blocks without application events, are saved atomically with the events and cursor. Pages read only SQLite and remain available when the node is offline or has pruned those blocks. Any current ingestion gap remains visible in the response.

Existing databases acquire the block table automatically. Historical page boundaries can fall back to hashes in retained events or cursors. An older empty block without retained hash evidence produces HTTP503 with an explicit gap; the consumer must not advance past it. Recover that hash from authoritative retained/archive evidence rather than guessing or clearing the database. Full-history reads can still use the retained latest cursor. Automated refund totals require an actual successful Cronpot execution and matching refund event in the same transaction context, not merely a refund event.

The authenticated `/api/evidence` backend stores content-addressed JPEG/PNG/WebP files on persistent disk. Set `EVIDENCE_BACKEND_TOKEN`, `EVIDENCE_DIR` and optionally `EVIDENCE_STORAGE_LIMIT_BYTES` (default250MiB). Each file is limited to5MiB and checked on upload and read.

Environment: `RELAYER_SEED`, `READ_ONLY`, `DEPLOYMENT_MANIFEST` (defaults to `deployments/portaldot-v3.json`), `WSS_URL`, `EVM_RPC_URL`, `CHAIN_TIMEOUT_MS` (45000), `CRONPOT_ADDRESS`, `METERMEND_ADDRESS`, `START_BLOCK`, `MODE`, `DB_PATH`, `PORT` (8787), and evidence settings. Addresses/start block normally come from the manifest. Do not start at a later block simply to hide an ingestion gap. `/health` exposes the configured `startBlock`, `writesEnabled`, execution profile, retained cursor and any gap.

For this initial MeterMend deployment, `deployments/indexer-bootstrap.json` records the explicit start at block 271379. The finalized read-back at 271384 showed `Cronpot.nextJobId == 1`, establishing that no Cronpot jobs existed before the new MeterMend deployment. Scanning includes the deployment block and every subsequent block. This exception does not claim unrelated earlier Scheduler history, clear an existing cursor, or permit skipping a later ingestion gap. The observed RPC metadata initialization timeout may require `CHAIN_TIMEOUT_MS=120000`; it does not change transaction retry policy.
